# 数据空间（data-space）

测试资产的台账：把「哪个项目、哪个模块、哪个功能」下的用例、步骤、预期，以及每个项目的环境地址集中记到一处，避免用例散落在表格、聊天和文档里各说一套。

- 顶栏一级入口（与「对话 / 终端 / Git」平级），可在「插件管理」里关掉。
- 演示版本只做「记下来 + 找得到 + 导出得了」，不执行用例、不连测试环境、不生成报告。
- 数据全局一份，不按项目/会话隔离；换会话、换项目读到的是同一批数据。

## 三层结构

```
项目（system，界面叫「项目」，字段名仍为 systemId）
├─ 模块（module）
│  └─ 功能（feature）   ← 用例的挂载点
│     └─ 用例（case）
└─ 环境（env）：本地 / 测试环境 / 预发环境 / 生产…（名称 + 地址 + 备注，可设默认）
```

例：`项目管理系统 / 合同管理 / 经营合同` 下面挂「新建经营合同-必填项完整可保存」这条用例；它的环境地址挂在项目「项目管理系统」下，不用每条用例重复写域名。

层级只存父引用（`systemId` / `moduleId` / `featureId`），不存嵌套数组——搜索、移动节点、导入导出都简单，悬空引用在服务端统一清洗。字段名继续用 `systemId` 是为了兼容旧数据与迁移逻辑，界面上统一叫「项目」。

## 五个页面

| 页面     | 作用                                                                                                                                                           |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 概览     | 项目 / 功能 / 用例 / 环境数量、功能覆盖率（有用例的功能占比）、按类型与按项目分布、覆盖缺口、最近更新。                                                        |
| 用例库   | 左侧是**项目列表**（可按名称 / 编号 / 说明搜索），进项目后用模块、功能两级 chips 下钻，右侧用例表；支持编号 / 标题 / 类型 / 标签搜索，优先级、状态、类型筛选。 |
| 执行结果 | 全部执行流水的集中入口：统计卡、搜索 / 结论 / 来源 / 时间筛选、「流水」与「按任务」两种看法的切换、CSV 导出（0.6.0）。                                         |
| 环境     | 每个项目一套环境（本地 / 测试 / 预发 / 生产）：名称、地址、备注，可按项目筛选，新建 / 编辑 / 复制 / 删除。                                                     |
| 设置     | 数据文件路径、导入 / 导出 JSON、恢复示例数据、清空执行记录、当前 revision、维护提示。                                                                          |

用例字段：编号（按项目 code 前缀自动生成，如 `PMS-004`）、标题、优先级 `P0~P3`、类型、状态（草稿 / 待评审 / 已评审 / 已废弃）、负责人、标签、前置条件、步骤（操作 → 预期，多步）、备注。

### 为什么要项目列表

项目一多，三层树全部展开会很长，翻找成本高。所以左栏只列项目（带颜色点、模块 / 功能 / 接口 / UI 用例计数、搜索框），进去之后再在项目内用 chips 选模块 → 功能，路径放在标题上方当面包屑。用例表里路径降为标题下方的小字，另加一列「类型」。

### 用例类型

当前只做两类：**接口** 与 **UI**。类型是开放词表——服务端 `GET /state` 下发 `caseTypes`，前端筛选 chips、下拉选项、徽章都从它取，后续追加类型（性能、兼容等）只需改 `model.mjs` 的 `CASE_TYPES` 一处。

保存时类型为空会补成 `接口`；但旧数据里已有的其他类型（如 0.2.0 的「功能」）**不会被改写**，仍按原值展示为灰色徽章，也不会在筛选里消失。

「覆盖缺口」列的是还没有任何用例的功能，点一下直接跳到该功能下新建用例——这是本页的主要用法：先看缺口，再补用例。

删除节点只删层级：删项目会连带删它的模块、功能与这个项目的环境，但用例不删，退回「未归类」，编辑时选一个新功能即可归位。

## 引入到 AI 对话（0.4.0 起）

用例堆在台账里只是「记下来」，真正要跑起来得进对话。现在可以在用例库里直接把用例带进 AI 对话框：

| 入口               | 位置                     | 带什么                                                 |
| ------------------ | ------------------------ | ------------------------------------------------------ |
| 单条               | 用例行最左侧的对话框图标 | 这一条（卡片档）                                       |
| 功能 / 模块 / 项目 | 页头「引入对话 · N 条」  | **当前可见范围**（跟着搜索、优先级、状态、类型筛选走） |

点开是一个确认弹窗：范围摘要、档位、末尾指令、脱敏与去重开关、完整文本预览。点「放入输入框」只把内容塞进对话框草稿并把视图切到对话，**不自动发送**——你通常要补一句自己的要求再发。

### 三档格式

- **卡片档**（≤3 条自动用）：每条带路径、类型、优先级、状态、负责人、前置条件、逐条「操作 → 预期」、关联数据、备注。
- **清单档**（更多条自动用）：按功能分组的表格，一行一条（编号 / 标题 / 类型 / 优先级 / 状态 / 步骤数）。
- **引用档**（0.5.0 新增）：只给「编号 · 标题（类型 · 优先级 · 状态）」一行一条，明细留给 AI 用 `data_space_cases` 现查。

上限：卡片 20 条、清单 200 条、引用 200 条，超出部分会提示「其余请分批引入」。也可以在弹窗里手动切档位。

什么时候用引用档：整功能几十上百条时，卡片档会塞满上万字，模型注意力反而分散。引用档只告诉模型「有哪几条」，真要执行时它自己按需取详情——上下文更省，且这轮改了用例也不会拿旧正文当新内容。

### 末尾指令

`执行测试` / `转自动化` / `用例评审` / `补充用例` / `不加指令`，只换最后那句指令，前面的用例内容不变，用户改几个字就能发。

### 三个刻意的细节

1. **机器可读锚点**：文本末尾有一行 `<!-- data-space: revision=49 cases=c-1,c-2 -->`，后续「执行结果回写」靠它定位是哪几条用例、什么版本。
2. **脱敏默认开**：`密码 / token / 密钥 / 口令` 这类键值在文本里打成 `***`；环境只带名称与地址，不带任何账号口令（注入就进了模型上下文与历史记录）。
3. **去重**：本轮已引入的用例在表里显示「已引入」徽章，弹窗默认跳过它们；数据一改（`revision` 变）徽章自动消失，不会拿旧内容当新内容。

执行本身不在本插件里做：接口类交给接口自动化流程，UI 类交给 UI 测试流程——数据空间的定位是「提供上下文 + 接回结果」。

依赖宿主的 `compose()`（宿主 API v2+，即 `window.__piWebUiHost`）：不支持时内容会复制到剪贴板并在提示里说明，不会静默丢。

## `@` 提及用例（0.5.0）

在对话框里输入 `@`，多一个来源「数据空间用例」：

- 输编号（`PMS-004`）精确命中排最前；输编号前缀、标题、负责人、标签、功能 / 模块 / 项目名都能搜；
- 空查询列出最近更新的 6 条（刚改过的最容易想起来）；
- 选中一条插入的是 `「用例 PMS-004 · 标题」`，不是整条内容——明细仍由 AI 用工具查，输入框不会被几万字占满；
- 命中的是功能 / 模块名时，额外给一行「整功能 / 整模块」项，写的是「全部 N 条用例」，后面接一句要求让它自己拉。

数据来源两路：页面打开过就用内存里那份（刚保存立刻可搜），没打开过则后台取一次快照并缓存 8 秒，不阻塞补全。

## AI 工具（0.5.0）

插件向 Agent 注册两个工具（需在插件设置里授权 `tools`）：

| 工具                       | 干什么                                                                                                                  |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `data_space_cases`         | 按项目 / 模块 / 功能 / 类型 / 状态 / 优先级 / 负责人 / 关键词 / 最近结果查用例；`action=list\|get\|stats`               |
| `data_space_record_result` | 回写执行结果（`results: [{ case, verdict, note }]`，结论为通过 / 失败 / 阻塞，可带 `env`）；`task` 给这批结果起个任务名 |

刻意约束：

- 查询工具**只读**，不会改用户数据；
- 工具结果里环境**只带名称与地址**，避开让口令、账号顺着工具结果进模型上下文；
- 回写只追加流水，不碰「用户编辑的内容」，因此不会和页面保存抢 `revision`；
- 用例后来被改过，旧结果按「用例已更新，结果可能过期」附注，不当现行结论。

## 执行结果与通过率（0.5.0）

- 用例表新增「最近结果」列：未执行是虚线按钮，点开登记通过 / 失败 / 阻塞，可写一句备注；也可以从概览的「需要跟进」直接点。
- 概览新增「通过率」卡片与执行结果进度条（通过 / 失败 / 阻塞 / 未执行）。
- **未执行不进分母**：新库通过率不会显示成 0% 误导人；分母是「已执行用例」。
- AI 回写的结果与手工登记的走同一条流水，谁后写谁生效（`at` 晚者胜）。

## 执行结果页（0.6.0）

用例表的「最近结果」只看得到每条的最新一次，回看「上周那轮 P0 到底哪几条挂了」没有入口。0.6.0 补了顶栏的「执行结果」页，读的是同一份 `runs.json`，只展示不改数据。

**统计卡**（跟随筛选）：执行记录条数、覆盖用例数、通过率、需要跟进（失败 + 阻塞）、最近执行时间。

**筛选与导出**：关键词搜编号 / 标题 / 备注 / 任务名 / 环境 / 路径；结论、环境、来源（AI 回写 / 手工登记）、时间范围（今天 / 近 7 天 / 近 30 天 / 全部）可叠加；「导出 CSV」导的是**当前筛出**的记录，带 BOM 便于 Excel 直接打开中文。

**两种看法**：

| 视图   | 适用                                   | 细节                                                                                            |
| ------ | -------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 流水   | 时间线式回看「谁什么时候改了什么结论」 | 一行一条，时间 / 结论 / 环境 / 用例 / 路径 / 来源 / 任务 / 备注；行尾可「重新登记」或引入对话。 |
| 按任务 | 回看「这一轮跑下来整批什么情况」       | 一个任务一张卡：通过率条、三态计数、逐条明细（超过 8 条折叠）；同批用例一眼看完，不必逐行筛。   |

**任务是怎么来的**：AI 一次回写多条（同一批）自动归为一个任务，默认名 `批量执行 MM-DD HH:mm`；也可以在调用工具时用 `task` 指定名字（如「经营合同 P0 回归」）。单条回写不造任务，手工登记在「按任务」视图里归到「单条登记」——不为了好看把零散记录硬凑成批次。

**旧结果怎么办**：用例改过（`updatedAt` 晚于记录）的标「可能过期」，不隐藏也不当现行结论；用例被删的记录在页面上显示「用例已删除」但仍可导出。恢复示例数据会连执行记录一起清空——用例 id 全新，旧流水已经没有引用价值。

### 示例执行记录（0.7.0）

空台账时页面只有一句空态，看不出统计卡、任务分组、过期降级长什么样。0.7.0 在空态加了「载入示例记录」：按当前库里真实的用例生成 11 条流水——3 个批量任务（含一条失败、一条阻塞、一条失败后复测转通过）+ 2 条手工单条登记 + 1 条「可能过期」，一次性把页面所有形态走一遍。

两条约束是刻意的：**只在空台账可用**（已有记录时页面与服务端都拒绝，避免演示用的假结论混进真实台账）、**不改用例**（只写 `runs.json`）。用完在「设置 → 执行记录」点「清空执行记录」即可回到空台账；也会随「恢复示例数据」一起清空。

## 项目环境（0.8.0）

用例要知道「跑在哪个环境」，但地址、账号这类东西不适合写进每条用例，也不适合让 AI 带进上下文。所以环境挂在项目下，一个项目一套：

| 字段 | 说明                                                                               |
| ---- | ---------------------------------------------------------------------------------- |
| 名称 | `本地 / 测试环境 / 预发环境 / 生产` 等，只做输入建议，可自由命名；同项目内重名被拦 |
| 地址 | 基础域名 / 前缀（去尾 `/`），只写地址，不写账号口令                                |
| 备注 | 一句话补充（如「数据每早重置」「仅内网」）                                         |
| 默认 | 每个项目最多一个默认，新建时自动带上；删掉默认会自动补下一个                       |

使用方式：

- 项目页头有「环境 · N」按钮和「默认环境」摘要，点一下直接进环境页并按该项目筛好；
- 登记执行结果（单条或 AI 回写）时选环境，默认取上次这条用例用的环境；
- 执行结果页多一列「环境」，工具栏可按环境筛选，CSV 也带上；按任务看时，整批同环境才在卡片头上标出来；
- 引入对话时只写环境名与地址（`- 环境：测试环境 · https://…`），不代任何账号；
- 工具回写时传环境名或 id 都能识别（大小写不敏感），认不出就按你写的名字存下，不催你造环境。

### 为什么删掉了「数据集」

0.7.0 及之前有一个「数据集」页：按功能归类的一堆键值记录。实际用下来两个问题：一是它跟用例的关系靠手动关联维护，用得少就变成死数据；二是真正需要跨用例共享的是「这套环境在哪、叫什么」，而键值对本身就不应该进模型上下文。0.8.0 用项目级环境替掉它，旧库里的数据集**不迁移**，但会先备份再丢弃，设置页会写明备份文件名与清理数量。

## 数据放在哪

```
<dataDir>/data-space/store.json    # 用户编辑的内容（项目 / 模块 / 功能 / 用例 / 环境）
<dataDir>/data-space/runs.json     # 执行结果流水（只追加，最多 800 条）
```

两份文件分开的理由：`store.json` 是「整份保存 + `baseRevision` 乐观锁」的编辑数据，`runs.json` 是流水。混在一起会让 AI 回写一次结果就把页面的 `baseRevision` 顶掉，变成保存冲突。

`<dataDir>` 就是 `PI_WEB_DATA_DIR`（默认 `~/.pi-web`）。放在这里而不是插件目录，是为了让插件升级、重装、卸载都不会碰用户数据。「设置」页会显示当前的真实路径。

结构（`JSON.stringify(…, null, "\t")`，可手改）：


- `systemId` / `moduleId` / `featureId` 为空或指向不存在的节点时，服务端保存时会把这条数据丢掉（模块、功能）或置空归属（用例）；`env.systemId` 悬空的环境直接丢弃。

- 单个文件上限：项目 60 / 模块 240 / 功能 720 / 用例 3000 / 环境 300（全局），每条用例 60 步、12 个标签。演示版够用，真超了再拆文件。

## 与旧版本的差异

0.1.0 只有「分组 + 数据集」（`version: 1`）。新版本读到时自动迁移：

- 每个分组变成一个系统（`code` 留空、颜色保留）；
- 旧文件先备份为 `store.json.v1-<时间戳>.bak`，迁移结果立刻落盘，只迁移一次；
- 页面「概览」「设置」会显示迁移提示，直到下一次保存（之后 `migratedFrom` 归零）。

0.7.0 → 0.8.0 的「去掉数据集」也是自动的：读到 `version < 3`、且还有 `datasets` 或用例上的 `datasetIds` 时，先备份 `store.json.v2-<时间戳>.bak`，再把数据写入 `version: 3`，清掉的数据量记在 `purged` 里（设置页可见，随下一次保存保留）。这一步不需要手动改文件。

旧格式 `{ groups, datasets }` 的 JSON 也能从「设置 → 导入」进来，导入时按同样规则转换（旧 dataset 直接丢弃）。

0.2.0 → 0.3.0 只是界面与类型调整：左树改成项目列表、类型收敛到接口 / UI，存储结构仍是 `version: 2`，无需迁移。0.3.1 是布局精简：去掉页内标题区、项目描述与统计合一行；标题栏只留一级导航与右侧状态文字。0.4.0 新增「引入到 AI 对话」：单条 / 当前范围两个入口、两档格式、末尾指令、脱敏与去重。0.5.0 新增引用档、「`@` 提及用例」、两个 Agent 工具、执行结果回写与通过率；`store.json` 结构不变，结果另存 `runs.json`（旧库首次打开就是空流水，不需要迁移）。0.6.0 新增「执行结果」页（统计卡、筛选、流水 / 按任务两种视图、CSV 导出）。0.7.0 补空台账预览：一键载入示例执行记录、设置里可清空流水（同样不碰 `store.json`）。0.8.0 移除「数据集」，改成项目级「环境」：登记结果可标环境、结果页与 CSV 带环境、AI 回写可传 `env`；`store.json` 升到 `version: 3`（旧数据集备份后丢弃，见上）。

## 写入与并发

整份快照提交 + `baseRevision` 乐观锁：

- `POST /plugins-api/data-space/save`，body `{ baseRevision, systems, modules, features, cases, envs }`；
- 版本对得上 → 清洗、落盘并 `revision + 1`；
- 版本对不上 → `409 { code: "conflict", store }`，前端载入返回的最新快照并提示重新修改（不静默覆盖）；
- `POST /plugins-api/data-space/reset`，必须 `{ confirm: true }`，回到示例数据。
- `POST /plugins-api/data-space/runs`，body `{ caseId | code, verdict, note, env }` 或 `{ results: [{ case, verdict, note, env }] }`：追加执行结果并 `runsRevision + 1`，未知用例返回 400 并回带 `unknown`。
- `POST /plugins-api/data-space/runs/demo`，必须 `{ confirm: true }` 且当前流水为空：按现有用例生成示例记录（已有记录返回 409，无用例返回 400）。
- `POST /plugins-api/data-space/runs/clear`，必须 `{ confirm: true }`：清空 `runs.json`（不动用例），返回 `removed`。

落盘走 `store.json.tmp.<pid>` + rename（`runs.json` 同样），写入中途崩溃不会留下半份文件；文件解析失败时会被隔离成 `store.json.corrupt-<时间戳>` / `runs.json.corrupt-<时间戳>`，内容从空开始（不会因此打不开页面）。

页面之间的一致性靠 `host.broadcast`：AI 回写结果后，已打开的数据空间页收到 `{ kind: "runs", revision }` 就重新拉一次快照并重绘，不用手动刷新。
