# API 测试工作流

使用可用的 `api_test_execute` 工具。若不可用，报告缺失的插件或引擎能力；不得改用直接 HTTP 请求或原始 MCP 调用执行。

## 支持范围与前置条件

当前支持带内部引用、响应为 JSON 的本地 OpenAPI 3.0 JSON 契约。目标须明确指定为端口 >=8900 的 HTTP `127.0.0.1` fixture，或由宿主为当前项目配置的单个手动 HTTP 数字 IPv4 源地址。仅有可写环境授权，并不意味着已配置目标或已提供测试鉴权与数据。暂不支持 DNS/TLS，已配置的目标不能用于定时执行。宿主可从运维配置文件读取专用、有有效期的令牌，仅注入执行内存。不得要求在工具参数、用例、模型提示词或证据中提供令牌值；缺少专用鉴权时仍须标记为阻塞。

## 主流程（按序执行）

### 步骤 1 · 生成用例

以跑通基础流程为目标，为选定接口各生成 1–2 条用例：先覆盖正常请求，资料充分时补一条必填项缺失或简单边界用例，暂不追求完整覆盖。优先复用接口文档和现有测试数据；断言先检查文档已明确的成功状态、必要字段或字段类型，复杂业务规则后续逐步补充。信息不足时列出待补充项，继续生成其他资料完整的用例，不因缺少非关键规则阻塞整个任务；不确定的预期不写成确定断言。用例保留工具要求的 `id`、`operationId`、`request`、`status`、`checks`；检查使用 `kind`（`exists`/`type`/`enum`/`value`）、JSON `pointer` 及适用的 `value`。缺少执行必需的鉴权、数据或响应定义时，可保留草稿并说明暂不能执行的原因。

每批 `operationIds` 和 `cases` 均不超过 3 项；超出时在生成阶段拆批，不通过新建工作流绕过已有评审、修订或时限预算。

`request` 仅接受 `path`、`query`、`body`，按契约需要提供；`path` 和 `query` 为参数对象。HTTP 方法及 URL 从 `operationId` 对应的契约派生，不传 `method`，不把 URL 字符串作为 `path`。

输出：`cases` 数组（`id`/`operationId`/`request`/`status`/`checks`）与待补充项清单。

### 步骤 2 · 准备套件

调用 `prepare`，传入 `sourcePath`、`operationIds`、`cases`、`rules`、`baseUrl`，以及项目内新的 `outputPath`。将返回的 `workflowRef` 保存为 `runRef`，并保留证据路径。准备完成不代表获准执行。

输出：`runRef`（保存 `workflowRef`）、证据路径、`outputPath`。

### 步骤 3 · 录入用例库（可选，需用户确认）

取得原生 draft 引用后提供入库选项；未获同意不导入，已明确要求本批录入时直接办理：

[[action:suggest:录入用例库,prompt=将本批生成的测试用例录入所选测试环境所属项目的用例库]]
[[action:suggest:暂不录入,prompt=本批生成的测试用例暂不录入用例库]]

选择录入后读 `data-space-testing` Skill 核对 `data_space_automation` schema。显式调用 `import`，`engine: "api"`，`assetRef` 取工具返回且宿主支持的原生 draft 引用；不用 `workflowRef`、`runRef` 或自造 JSON 充作 draft 引用。按所选 `envId` 匹配所属 `systemId`，保留显式或既有通道 `featureId`；无指定目录默认“测试用例 → API用例”，缺则建、有则复用，重命名后跟随目录 ID。`moduleName`/`featureName`/`envId`/`featureId` 以实际 schema 为准；缺能力或引用时明确阻塞，不绕过核验。

录入 draft 只存草稿：不建自动化绑定、不执行、不写结果、不代表已冻结或获批。无原生引用的人工用例不承诺任意 JSON 入库。正式批次结果仍走 `sync`；暂不录入不改变评审与执行规则。

输出：draft 的 `assetRef` 与目录位置；暂不录入时本步跳过，`runRef` 与后续步骤不变。

### 步骤 4 · 评审

调用 `review`。

输出：结构化问题清单（用例 ID、问题维度、依据）。

### 步骤 5 · 定向修订

按评审结果仅对受影响用例调用 `revise`，保留原始契约与预期；每次修订输出新目录并重新评审。不得通过创建替代工作流重置限制：每个工作流最多 3 次评审调用、2 次修订，截止时限为 180 秒。

输出：新 `outputPath` 的修订套件，待重审。

### 步骤 6 · 执行

仅执行已批准的套件：action 用 `run`，传同一 `runRef`。

输出：`runId`、证据路径。

### 步骤 7 · 定向复测

用户要求复测时用同一 `runRef` 和明确 `priorRunId` 调用 `retest`；不得自动重试失败或结果未知的请求。写入未知时先查残留数据，再做后续执行；取消只停本次运行，不撤销已发生的数据变更。

输出：本次结果与 `priorRunId` 的逐用例对比。

### 步骤 8 · 报告与交付

使用 `report` 查看历史，不发送请求。交付证据路径、已执行/通过/失败/阻塞/未执行数量及清理状态。区分 fixture 验证、模型替身、真实模型评审和业务验收。工作流存于内存：重启后仅保留文件证据，不得声称可恢复执行。

输出：证据路径 + 六项计数（已执行/通过/失败/阻塞/未执行/清理状态）。

## 失败分支

- `api_test_execute` 不可用或无受控执行上下文 → 一线：报告缺失插件能力，停本步；兜底：请宿主启用插件，不改直连 HTTP 或原始 MCP。
- 契约缺 `operationId`、响应定义或必需鉴权与数据 → 一线：保留草稿、列待补充项，先做完整接口；兜底：该用例标阻塞，不写成确定断言。
- 专用令牌未由宿主配置 → 一线：标记本批阻塞；兜底：请运维在宿主侧配置令牌，不索取令牌值。
- `prepare` 报参数或契约错误 → 一线：核对 `operationIds`/`cases` ≤3、`baseUrl` 与端口规则后重试一次；兜底：拆批后仍失败报错误原文并停。
- 已用满 2 次修订或 180 秒时限 → 一线：停修订，交付未解决问题与证据；兜底：交人工决策，不新建工作流。
- 写入未知或清理失败 → 一线：查残留数据并记录范围；兜底：未清则停后续执行，报残留，不重试。
- `run` 被拒（未获批）→ 一线：回步骤 4 补评审批准；兜底：报原因，不执行、不改直连。

## 不要做

- 用直连 HTTP 或原始 MCP 代替 `api_test_execute`。
- 为凑通过放宽断言或改写预期。
- 把令牌写入工具参数、用例、提示词或证据。
- 自动重试或连跑失败/未知结果的请求。
- 新建工作流绕过评审、修订或时限预算。
- 未获批准就 `run`。
