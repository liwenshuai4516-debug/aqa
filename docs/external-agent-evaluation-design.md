# 外部 Agent 客户端与项目评估：接入设计与实施计划

日期：2026-10-23；状态：设计，未安装外部评估框架、未启动外部 Agent、未调用收费模型。

本文件扩展 [Agent 评估中心总体计划](agent-evaluation-design-plan.md)，沿用任务契约、证据快照、逐项判定和人工复核。用户已明确第一批优先评估**本地或命令行 Agent 客户端**。本方案负责外部接入，不另建评分中心。

本次仓库核对：已有总体设计文档、宿主事件及 UI/API 证据基础，尚未检索到总体计划中拟新增的 `agent-evaluation` 实现模块；不据此认定用户其他环境也未实现。开始接入时先确认实际可复用版本，接口不齐就列前置缺口，不将规划标为完成。

## 1. 核心决定

1. 外部 Agent 作为被测系统，通过适配器接入，保留其原有任务执行循环；评估平台负责准备样本、控制运行、收集证据和独立验收。
2. 首批优先支持无交互模式的 CLI；只有交互终端的 TUI、外部 API、可插桩项目、网页/桌面界面分批接入。
3. 结果正确性与过程可观测性分开。没有工具日志仍可核验产物，但不能声称评估了全部工具行为。
4. 优先验证 Harbor 现有接入和 ATIF 导入的复用价值，再决定是否为某个客户端写直接 CLI 适配器；不同时引入多套大型执行框架。
5. 最终结果由平台持有的独立校验器验证。进程退出0、客户端自报完成、外部框架 reward 或 trace schema 合法均不单独证明业务成功。
6. 独立工作目录只隔离文件布局，不构成安全沙箱。执行级隔离、配置隔离、凭据范围和停止能力单独声明与验证。

## 2. 评估对象与适用能力

| 外部对象                  | 接入方法                                           | 能直接评价                                         | 不能直接证明                               |
| ------------------------- | -------------------------------------------------- | -------------------------------------------------- | ------------------------------------------ |
| 无交互 CLI 客户端         | 原生 JSON/JSONL、stdout/stderr、进程句柄、产物快照 | 输出、产物、结束状态、总耗时；有日志时评价部分过程 | 未输出的模型/工具行为，真实提供者账单      |
| 仅交互 TUI                | 专用 PTY 会话、有限状态适配器、人工响应记录        | 可见交互、产物、阻塞与恢复                         | 终端静默即完成；隐藏内部状态               |
| 有 API 的 Agent 服务      | HTTP/流式接口、远端任务ID、状态/取消/结果查询      | 服务响应与任务结果；有业务接口时回查               | HTTP200或连接关闭代表任务达成              |
| 可修改源码的 Agent 项目   | SDK接入、OTel/OpenInference插桩、原生事件导出      | 已插桩路径的模型、工具、委派和性能                 | 未覆盖执行路径；采样trace的完整性          |
| 只能操作的网页/桌面客户端 | 隔离账号/桌面，Playwright或OS可访问性/图像驱动     | 端到端结果、可见体验、产物                         | 内部token、隐藏重试、完整工具链            |
| 只有导出日志/结果包       | 离线导入及来源校验                                 | 有证据范围内的历史分析                             | 当前实际运行、历史外部状态或日志绝对真实性 |

针对“Agent客户端”必须区分两个测试对象：用它完成任务是在评估Agent系统能力；测试登录、菜单、窗口等是在测试客户端软件质量。两者可共用UI测试技术，但样本、指标和报告分别标识。

## 4. 证据能力声明与可信边界

每个TargetProfile记录如下能力，每项状态为 `supported / partial / unsupported / unknown`，并附实际验证版本和证据：

- 非交互启动、输入协议、最终事件与进程结束；
- 单任务会话隔离、配置/记忆隔离；
- 输出、工具事件、模型usage、子代理、权限/审批记录；
- 本地与远端取消、进程树收尾、断线重连；
- 文件/业务状态核验、网络限制、模型替换；
- 轨迹导出/导入、恢复旧会话，分别声明。

来源标记区分 `harness-observed`（平台观察）、`target-reported`（客户端自报）、`instrumented`（插桩）、`externally-verified`（独立校验）、`human-observed`。这些不是绝对等级，按具体规则选择依据。

例如，客户端报告一次工具调用，只证明它输出了该事件；平台在隔离目录读取结果，才支持相应文件确实存在。外部工具调用记录缺失时，“没有违规调用”不能判pass；受限制路径不可访问的环境测试可以证明隔离有效，但不能推断模型没有尝试。

trace采样、字段裁剪、未关联子代理和远端后台工作均进入覆盖缺口。未知费用不是0；外部账单未核验时只显示所报告/估算金额。

## 5. 整体接入流程

```mermaid
flowchart LR
    T[目标客户端及能力探测] --> P[固定样本与独立环境]
    P --> E[ExecutionAdapter]
    E --> A[外部Agent原执行循环]
    A --> C[原生日志与EvidenceAdapter]
    A --> O[输出文件或业务状态]
    O --> V[独立Verifier]
    C --> S[已有评估证据快照]
    V --> S
    S --> R[规则评估与对比报告]
```

一次trial顺序：准备 → 预检 → 提交任务 → 执行/等待交互 → 确认停止 → 收集最终产物 → 独立核验 → 评分 → 清理与报告。执行中日志可增量收集；产物最终快照须在停止/一致性条件满足后取得。

被测执行与校验完全分开：被测Agent不能写平台评分记录或修改可信校验器。被测代码可能恶意执行，Verifier也必须在隔离环境中运行，不在宿主直接运行外部提交的代码。

## 6. CLI首批具体工程设计

### 6.1 TargetProfile与启动

最小配置包含：`targetId/adapterId/adapterVersion/clientVersion/binaryIdentity/launchSpec/configRef/capabilities/isolationProfile/credentialRef`。

launchSpec使用可执行文件与参数数组、stdin或私有输入文件，禁止拼接shell字符串。任务文本不插值成命令，密钥不进入命令行、日志或仓库。参数来自该客户端经过验证的原生协议，不发明通用的`--json`或`--workspace`标志。

预检核对文件身份、客户端版本、支持参数、非交互模式、工作目录、配置路径和必要运行时。无效版本/参数直接记setup_error，不先花模型额度试错。CLI升级后旧解析器未获兼容验证则回退为有限观测或阻塞，不能静默错读。

首版不自动登录或复制个人认证目录。使用用户明确提供的专用配置/凭据引用；若客户端只能使用已有个人登录且无法隔离，标记限制，不自动进入无人值守批量评测。环境变量继承采用白名单，敏感参数只在执行层注入。

### 6.2 环境与文件隔离

每个trial有独立fixture工作目录、客户端可配置的会话/缓存目录和平台证据目录。二进制/依赖尽量复用锁定只读版本，不复制整份依赖进入证据。

工作区分离不是权限隔离；代码修改和工具执行类批量测试需要已验证的容器/虚拟机或OS约束。无可靠隔离时仅允许已明确限定风险的人工试点，不标为安全批量能力。容器内CLI表现要标明运行平台，不能代替macOS原生客户端验收。

Git任务使用固定提交与明确输入文件生成干净副本；不修改用户现有仓库。产物采集覆盖允许的修改、新增和删除，并记录必要的忽略文件，不能只看`git diff`漏掉未跟踪输出。导出拒绝越界/符号链接逃逸，不跟随外部路径读取个人文件。

平台证据、隐藏校验规则与评测结果不放在Agent可写目录。对平台只读目录、进程和网络的隔离要求在probe中实际验证。账户、原生MCP、网络及提供者内置工具能力逐项记录；本地断网不自动保证提供者远端工具无法联网。

### 6.3 流式日志、结束与恢复

直接模式用管道优先：stdout/stderr分别分块读取，流式解析JSONL，支持半行、UTF-8分片、混合诊断文本、未知事件和有界超大行。保留受控原日志及解析缺口，不因格式错误丢掉整次已产生产物的试验。

进程成功退出表示 `execution ended`；目标pass仍需Verifier证据。最终文本先到但进程未结束时继续等待；静默不是完成。认证或审批提示进入 waiting-input，默认不自动同意；超时记录干预缺失，不伪装为模型任务失败。

停止流程：发该实例的取消 → 等待短宽限 → 必要时只终止该实例受控进程树/容器 → 验证退出与日志封存。禁止按进程名称全局清理。杀掉CLI不代表远端模型/工具已取消；远端不可核验时标remote-stop-unknown，阻塞可能产生冲突的后续写任务。

服务重启不自动重新提交旧任务。用持久trialId与执行句柄查询存活状态，能重新附着则恢复采集，否则interrupted；不能仅靠PID匹配，须核对启动身份以防PID复用。未确认停止不取会被持续写入的最终产物快照。

### 6.4 独立Verifier

Verifier是已有Evaluator体系中的确定性结果检查，不新建一套评分规则：

| 任务              | 独立核验                                                                              |
| ----------------- | ------------------------------------------------------------------------------------- |
| 代码修复          | 固定基线 + 产出patch，在新隔离环境执行平台持有的测试；记录patch、测试代码版本与原结果 |
| 文件生成/数据处理 | 直接解析输出结构、数量、内容和约束；不只检查文件存在                                  |
| 工具业务操作      | 用隔离服务的审计记录/只读状态核验目标及数量                                           |
| 只读分析          | 核验引用、结构化事实；语义取舍进入人工或后续模型评审                                  |

不把被测Agent自己修改后的测试全通过当作独立证明。公开开发测试允许用于任务；保留验收测试与标准答案在独立边界，防止被修改或直接读取。合法修改测试的任务也需由另一份可信验证集验收。

隐藏测试缺失、Verifier环境无法启动、patch无法核验等单列错误。禁止清除原失败证据后用一次成功覆盖。证明某条测试通过也不等于所有软件正确，报告明确覆盖范围。

## 7. 统一接口与工程落点

复用总体计划的三类接口，新增ExecutionAdapter仅因为本阶段需要受控运行外部对象；不提前构建远端调度平台。

| 接口              | 本次具体契约                                                                                                                                  |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| ExecutionAdapter  | `probe(profile)`、`prepare(trial)`、`start(input)`、`status(handle)`、`cancel(handle)`、`cleanup(handle)`；返回实际能力、句柄、阶段与收尾证据 |
| EvidenceAdapter   | 按游标读取CLI/ATIF/未来OTel，输出稳定来源引用、覆盖范围、缺口和原生格式版本                                                                   |
| Evaluator         | 用平台只读验证环境完成输出核验，不能读取Agent自填pass当结论                                                                                   |
| EvaluationProfile | 声明适用目标/样本、必要观测、Verifier与聚合规则；不支持项显示不可评价                                                                         |

稳定标识：`experimentId/trialId/attemptId/targetId/nativeSessionId/nativeRunId/traceId`保留映射，不按客户端任务标题去重。同nativeCallId在不同会话不得碰撞，导入同包幂等，重新执行必须新trial。

ATIF仅作交换格式，不替换内部原模型。保存原格式版本、适配器版本、原包摘要与转换丢失项；未知版本保留原包且拒绝未经核验的过程评分。导入包按数据解析，禁止执行内附脚本/安装依赖；限制包大小、解压数量、路径穿越和符号链接，不自动下载引用URL。

拟新增位置（均未创建）：

| 路径                                               | 用途                                                   |
| -------------------------------------------------- | ------------------------------------------------------ |
| `plugins/agent-evaluation/targets/`                | 目标客户端档案、能力声明和校验                         |
| `plugins/agent-evaluation/executors/`              | 首批选定的Harbor或直接CLI执行适配器                    |
| `plugins/agent-evaluation/adapters/atif.mjs`       | ATIF输入转换与证据范围                                 |
| `plugins/agent-evaluation/adapters/cli-events.mjs` | 首个客户端的结构化事件转换；不是任意CLI万能解析器      |
| `plugins/agent-evaluation/evaluators/`             | 复用总体规则，增加产物核验                             |
| `server/agent/external-evaluation-runtime.ts`      | 如现有受控进程能力不足，在宿主补最小启动/取消/隔离接口 |
| `tests/fixtures/external-agent-evaluation/`        | 无模型假CLI、可控子进程和独立Verifier                  |

跨端协议、工具注册、生命周期、插件启停、技能和桌面安装遵守总体计划与AGENTS规则。不在评估插件里直接绕过宿主运行任意命令。未来框架通过固定版本子进程/结果包桥接，避免把Node应用改造成Python执行平台。

## 8. 两种比较模式与指标

### 原生产品模式（首批默认）

保留客户端正常支持的模型、工具和配置，在固定任务/预算/环境下评价整个系统。记录实际版本、权限模式、提示词补丁、可访问工具、记忆/缓存和人工干预。不默认读取个人记忆；隐藏配置不可得时显示unknown。

结论是“该客户端配置在这批任务上的表现”，不能推导为底层模型能力排名。

### 受控框架模式（后续）

在支持条件下统一模型及服务端能力、任务输入、工具、预算和初态，借助Inspect Bridge等研究框架策略。模型代理可能影响API兼容、缓存、工具、延迟和成本，作为实验因素记录；不与原生模式结果混成排行榜。

### 指标

- 核心：任务达成率、适用规则判定覆盖率、错误/阻塞/未执行分布、独立Verifier结果。
- 效率：setup、Agent运行、verification、cleanup及端到端时间分别记录；客户端可观测usage与估算费用注明来源。
- 过程：仅对具备必要证据的目标评工具选择、重试、委派和权限行为；缺日志不能给高分或低分。
- 稳定性：首批可用重复样本展示成功次数和波动，不凭一次结果宣称稳健或显著优越。

预算以wall time和可控制的调用/输出约束为先；没有计费前置控制的客户端不承诺硬费用上限。账号限流、服务故障与目标决策分开。统一预算不等于统一实际执行条件，需要同时展示能力差异和共同可比样本集。

缓存、模拟、原生客户端、容器客户端与人工干预分别标识。评测保留集不反馈给客户端调试；公开benchmark结果只作该版本任务集上的证据，不能替代本项目真实场景。

## 9. 首批样本与用户操作

第一批先使用固定假CLI验证接线，再由用户指定两个真实CLI和授权的模型/账号执行相同10个隔离场景。假CLI不证明真实Agent能力。

| 场景                     | 预期与目的                         |
| ------------------------ | ---------------------------------- |
| 生成结构化文件           | 文件实际存在、字段/内容正确        |
| 修复小型代码缺陷         | 独立测试通过、改动范围正确         |
| 修改多文件但保留指定内容 | 差异和保护项检查                   |
| 读取资料后输出带引用结论 | 依据可核验、不编造文件             |
| 明确要求只读分析         | 无额外写入；需要平台可观测范围支持 |
| 输入不完整               | 按契约提问或说明阻塞，不猜关键数据 |
| 工具首次临时失败         | 允许有界恢复，保留失败与成功证据   |
| 环境永久不可用           | 停止依赖工作，不循环重试或声称完成 |
| 任务重复提交             | 隔离服务中的幂等与重复副作用核验   |
| 超时并产生子进程         | 平台取消/收尾可验证，剩余未知单列  |

这些是业务样本方向；10个场景中的故障行为还须由固定假CLI主动触发，以验证评估系统自身不会误判。真实模型不一定自然产生所有工程故障。

页面新增“评估对象”：选择连接方式 → 填写客户端路径/配置引用 → 探测能力 → 选择样本及环境 → 预览权限/预算/可评价范围 → 运行 → 查看产物与证据。结果页明确分为Agent结论、平台观察、独立核验和不可观测项。

已有日志导入提供独立入口，不触发启动、登录、安装或业务重放。

## 11. API、源码与界面接入的后续路线

API：注册目标端点、身份引用和任务协议；区分同步响应、异步run和事件流。支持请求幂等键或远端查询时优先使用；请求超时状态未知，不自动重发可能产生副作用的任务。取消无确认则保留远端未知。

源码项目：在模型/工具/委派真实边界插桩，导出OTel/OpenInference。记录schema版本、traceId、采样和导出flush；import正常不等于链路完整。OTel展示后端可用Phoenix/Langfuse，但本项目内部证据契约保持独立。

网页/桌面：驱动器只负责向被测客户端提交任务和观察，不代替Agent完成被测业务。设置独立账号、浏览器profile或VM，固定版本、分辨率和初态，记录驱动失败/验证码/人工协助。能用后台只读接口核验时优先使用；只有截图时只评价其支持的可见条件。

BrowserGym/OSWorld提供任务环境和评估方法，不自动支持任意封闭客户端。缺少可控输入、明确完成信号或可恢复初态时，先提供半自动/人工评估，不承诺无人值守批量测试。
