# D05：MCP 设置重启后仍调用旧客户端

状态：2026-10-20 用户明确批准这一行通知修复；已实施，单测及最新实际 DMG 安装包同会话重启调用复验通过。

新版实际 DMG 安装包已通过首会话 MCP 中文文件读取、实际写文件、越界拒绝、原生审批拒绝/批准，以及设置页禁用/启用的进程与配置检查。但在同一聊天中再次调用 MCP，返回「客户端已关闭，不会重启」。证据见 `evidence/T14-mcp-reenable-failure.json` 与同名日志。请求全部由本机脚本模型生成，没有真实供应商费用。

原 `McpBridge.reloadOnce()` 重建工具定义并关闭旧客户端，却没有发送已有的 `onToolsChanged` 通知。UI 操作会刷新服务器状态，已有聊天的执行闭包仍指向关闭的客户端。文件监视的 2000ms 轮询有时能补救，但在该轮询周期内完成禁用/启用后，最终配置与初始配置一致，轮询看不到变化。

最小提案：在新集合聚合完成并关闭旧客户端后，增加 `this.opts.onToolsChanged?.()` 一行，与原 `reaggregateTools()` 的通知语义保持一致。原 index.ts 已将该回调连接到现有会话工具刷新。适用于全部原调用方，不改 MCP 协议、权限、进程和执行语义。逐行差异见 `D05-proposed.patch`。

验证：保持新增的真实服务重启后同会话读文件断言；补充 bridge 单测确认 reload 返回前通知且新工具绑定新客户端；运行原 MCP 桥/热加载/插件单测、类型检查、实际安装包回归与受保护哈希核对。
