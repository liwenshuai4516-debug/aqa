## 结论与调整依据

**AC39 在当前历史批量采集范围按 `ec04-batch-v2` 通过，性能阻塞解除。** 原 v1 下并行/长输出仍失败；没有产品代码加速，不声称优化效果或统计显著。其他 EC04 产品验收和真实客户端不由此通过。

原跑器实际做的是：先用 1ms 定时器模拟 20/200/100 次任务等待，然后显式读取已有 SDK 调用/结果、脱敏、生成摘要并同步保存。关闭组没有归档工作；构造 fixture 在计时外。因关闭中位等待约几十至百余毫秒、CPU 仅数毫秒，20%/25% 加 50ms 下限在三类负载上实际都是 50ms。它既不是真实模型/工具耗时，也未测实时事件采集对任务的影响，不能把该比率解释为产品运行开销。

相同 50ms 限值覆盖约 10KB、100KB 和 20MB 输入，没有体现批量规模；大输入还包含必要的多次有界转换、摘要及持久同步。原标准可保留为优化参考线，但缺少把它设为所有批量交付硬门槛的用户体验依据。当前性能也不能证明原标准在技术上不可能达到；不再为满足这一参考线反复尝试已否决的局部优化。

本轮选择有限批量响应预算：小批 0.1 秒、多记录批处理四分之一秒、约 20MB 归档 1 秒，并对长输出另设 750ms CPU 上限。这是产品工程取舍，不是行业标准或供应商承诺；不从这几个结果外推高频 watch、事件循环延迟或任意机器性能。
